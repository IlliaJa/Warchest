# Пошук в умовах невизначеності (AlphaZero-стиль для Сундука Війни)

Розбір того, як `LookaheadCriticBot` та його родичі (`PolicyCriticBot`,
`RoundCriticBot`, і базовий `LookaheadBot`) обходять приховану інформацію гри —
**руку опонента** та **випадковий порядок добору монет** — з детальним поясненням
поточної апроксимації, прикладом, її фундаментальних недоліків і пропозиціями
кращих рішень.

Пов'язані документи: [bots.md](bots.md) (огляд ботів + журнал експериментів),
[lookahead_bot_plan.md](lookahead_bot_plan.md) (початковий дизайн пошуку),
[game_mechanics.md](game_mechanics.md), [rewards.md](rewards.md).

---

## 1. Що саме приховано в Сундуку Війни

У грі є рівно два джерела невизначеності, і важливо розрізняти їх точно:

1. **Порядок добору монет (draw order).** Мішок (`bag`) кожного гравця — це
   мультимножина монет з **публічно відомим складом**: обидва гравці знають,
   *які* монети лежать у чужому мішку (вони прийшли зі спільного supply через
   recruit, який усі бачать). Невідомо лише, у **якому порядку** вони будуть
   витягнуті. Тобто це невизначеність над перестановками відомої мультимножини,
   а не над самим складом.

2. **Рука опонента (opponent hand).** На початку раунду кожен гравець наосліп
   тягне `HAND_SIZE = 3` монети з мішка в руку ([game_state.py:16](../src/services/environment/game_state.py#L16)).
   Свою руку ти бачиш, чужу — ні. Але оскільки склад мішка публічний, «рука
   опонента» — це просто питання *які 3 з N відомих монет зараз у руці, а не в
   мішку*. Знову: невизначеність над **розбиттям** відомої множини, а не над її
   вмістом.

Обидва джерела зводяться до одного типу: **ми знаємо повний набір монет, не
знаємо лише їх поточне розташування (порядок/розбиття).** Це ключове
спостереження — воно робить гру набагато «легшою» для приблизного пошуку, ніж,
скажімо, покер, де приховані самі карти.

Додатково є дрібні chance-події всередині ходу (наприклад, бонусна монета Warrior
Priest — [warchest_env.py:978](../src/services/environment/warchest_env.py#L978)), які
йдуть через той самий `_draw_one`, тож апроксимація нижче покриває їх автоматично.

## 2. Поточна апроксимація: одна детермінізація на хід

Уся сім'я критик-ботів успадковує механізм у [LookaheadBot](../src/services/bots/lookahead_bot.py).
Ідея — **детермінізація** (determinization): замінити приховану випадковість
одним конкретно вгаданим «світом», зафіксувати його на весь пошук, і шукати в
ньому так, ніби гра з повною інформацією.

### 2.1 Порядок добору — фіксована черга на весь `act()`

Симуляційний рушій отримує підмінений метод добору
[`_determinized_draw_one`](../src/services/bots/lookahead_bot.py#L122):

```python
def _determinized_draw_one(sim_env, player):
    queue = sim_env._sim_draw_queues.get(player)
    if queue:
        coin = queue.pop()          # беремо наступну монету з наперед перемішаної черги
    else:
        coins = list(sim_env.state.bags[player].elements())
        coin = int(np.random.choice(coins))   # запасний варіант, якщо черга вичерпалась
    ...
```

На старті кожного `act()` [`_prepare_root`](../src/services/bots/lookahead_bot.py#L249)
один раз перемішує кожен мішок у чергу:

```python
queues = {
    root_player: self._shuffled(state.bags[root_player]),
    opp:         self._shuffled(state.bags[opp]),
}
```

Далі **ця сама черга** передається у кожну гілку дерева пошуку (кожен вузол
клонує чергу через `{1: list(queues[1]), 2: list(queues[2])}`, але порядок у ній
не змінюється). Тобто всі брати-гілки, які ще не витягли монету, бачать те саме
майбутнє. Це дешевше, ніж семплувати наново в кожному вузлі, і коректно в тому
сенсі, що невитрачена частина майбутнього спільна для сестринських ліній.

### 2.2 Рука опонента — два режими через один механізм

Прапорець `see_opponent_hand` (за замовчуванням `True`):

- **`True` (cheat / режим тиску):** пошук читає **справжню** руку опонента.
  Це і є режим за замовчуванням для критик-ботів, бо вони eval-only і критику ще
  дають привілейовані фічі (`get_privileged_features()` — обидві руки, обидва
  мішки), на яких він і тренувався.
- **`False` (fair):** справжню руку не використовуємо. Замість цього
  [`_prepare_root`](../src/services/bots/lookahead_bot.py#L257) **об'єднує** руку
  й мішок опонента в один пул і **перерозбиває його рівномірно-випадково**:

  ```python
  hand_size = sum(state.hands[opp].values())
  pool = list((state.hands[opp] + state.bags[opp]).elements())
  random.shuffle(pool)
  state.hands[opp] = Counter(pool[:hand_size])   # випадкові 3 монети "в руку"
  state.bags[opp]  = Counter(pool[hand_size:])   # решта — у мішок
  ```

  Після цього далі все однаково: з отриманого мішка семплюється черга добору. Один
  механізм на обидва режими, а не окремий оцінювач.

### 2.3 Усереднення по детермінізаціях (PIMC), поки що вимкнене

`LookaheadCriticBot` додає параметр `n_determinizations`
([lookahead_critic_bot.py:327](../src/services/bots/lookahead_critic_bot.py#L327)).
Ідея — не ставити все рішення на один вгаданий світ: розбити бюджет часу на
кілька незалежних пошуків, кожен під свіжою детермінізацією, і **проголосувати**.
Це класичний прийом **Perfect Information Monte Carlo (PIMC)** — усереднення по
детермінізаціях.

Проте за замовчуванням `n_determinizations=1` (вимкнено). У журналі експериментів
([bots.md](bots.md)) зафіксовано, що будь-яке розбиття бюджету виявилось **гіршим**
за один пошук: критик-пошук і так голодний на глибину (0.5 с дають глибину 0–3,
тоді як alpha-beta `LookaheadBot` за п'яту частину часу доходить до 4–6), тож
віддавати частину бюджету на хедж — програш. Навіть перекошене 80/20 не окупалось.
Тому код лишили, але за замовчуванням він робить один пошук з вагою `[1.0]`.

## 3. Приклад роботи детермінізації

Нехай на початку раунду мішок опонента (склад публічно відомий) містить:

```
bag(opp) = { Swordsman×2, Archer×1, Knight×1 }
```

**Крок 1 — детермінізація порядку.** `_prepare_root` один раз перемішує це в
чергу, наприклад:

```
queue(opp) = [Knight, Swordsman, Archer, Swordsman]   # зафіксовано на весь act()
```

**Крок 2 — пошук.** Дерево пошуку розгортає багато ліній гри. У *будь-якій* лінії,
де опонент добирає монету, він отримає монети саме в цьому порядку: спочатку
Knight, потім Swordsman, потім Archer… Розгляньмо дві сестринські гілки:

- Гілка A: наш хід змушує опонента добрати 1 монету → він гарантовано отримує
  **Knight**.
- Гілка B: інший наш хід → опонент добирає 2 монети → **Knight, потім Swordsman**.

Пошук ніколи в цьому `act()` не розгляне світ, де опонент першим тягне Archer, —
хоча в реальній грі це рівноймовірно. Якщо наше найкраще рішення чутливе до того,
*що саме* опонент дотягне (наприклад, Knight дає йому bolster-загрозу, а Archer —
ні), то оцінка гілки може «стрибнути» через один вгаданий кидок кубика, якого в
реальності не буде. Це **дисперсія однієї детермінізації** — чистий шум у рішенні,
а не сигнал.

**Крок 3 — рука опонента (fair-режим).** Якщо `see_opponent_hand=False`, то перед
усім цим ще й рука визначається випадково: з пулу `{Swordsman×2, Archer, Knight}`
(рука+мішок разом) 3 монети кидаються «в руку», 1 лишається в мішку — теж один
вгаданий варіант з кількох можливих.

`n_determinizations=k` частково лікує це: зробити k таких пошуків з різними
чергами/розбиттями й усереднити — тоді Archer-світ теж потрапить у вибірку і
рішення стане стійкішим. Але (див. §4) навіть це не усуває глибших вад методу.

## 4. Чому детермінізація — принципово недосконала

Детермінізація зводить гру з неповною інформацією до набору ігор з повною
інформацією. Це зручно, але має два добре відомі в літературі дефекти
(Frank & Basin; Long et al., «Understanding the Success of PIMC»):

### 4.1 Strategy fusion (злиття стратегій)

Розв'язуючи кожен детермінізований світ **окремо**, пошук неявно припускає, що
може обрати **різну** дію в різних світах — навіть якщо ці світи належать одному
й тому самому *інформаційному сету* (тобто ти їх не розрізняєш і мусиш зіграти
**одну** дію на всі). Пошук «зливає» кілька несумісних планів в один оптимістичний.

У Сундуку Війни: припустимо, оптимальний хід залежить від того, чи в руці
опонента зараз Knight. Пошук у світі-з-Knight обере контргру проти Knight, у
світі-без — інше; усереднення голосів вдає, ніби ми зможемо адаптуватись, хоча
насправді ми ходимо **до** того, як дізнаємось руку. Реальна цінність
«універсального» ходу занижується/завищується.

### 4.2 Non-locality (нелокальність)

У кожному детермінізованому світі опонент моделюється так, ніби він **знає** свій
(насправді прихований від нас) розклад ідеально — а іноді й наш. Значення
«протікають» із інформації, якої в реального гравця в цій позиції немає. Пошук
може боятися відповідей, які опонент зміг би знайти лише знаючи наш прихований
стан.

### 4.3 Рівномірне перерозбиття ігнорує наявну інформацію (fair-режим)

`_prepare_root` перерозбиває руку опонента **рівномірно**. Але гра постійно
зливає інформацію про руку: face-up скиди, зіграні монети (`discard_faceup`,
`last_coin`), історія recruit. Рівномірний пріор викидає це — насправді розподіл
руки опонента **умовний** на тому, що він уже показав. Правильно було б тримати
**belief state** (розподіл над руками), а не один рівномірний кидок.

> Практичний наслідок: режим за замовчуванням `see_opponent_hand=True` (підглядання)
> взагалі обходить 4.3 — але ціною того, що це вже не чесний агент. Для реальної гри
> (напр. `web_agent`) потрібен саме чесний режим із belief, а він зараз найслабший.

## 5. Як це співвідноситься з AlphaZero

AlphaZero = **MCTS** (пошук по дереву) + мережа, що дає **пріор ходів (policy)** та
**оцінку позиції (value)**, без будь-яких rollout-ів до кінця гри. У цьому репозиторії
вже є всі три інгредієнти, просто зібрані в іншу форму:

| Компонент AlphaZero | Аналог тут |
|---|---|
| Value-мережа | `Critic` → `LookaheadCriticBot` оцінює листя |
| Policy-пріор | `Policy` → `PolicyCriticBot._prune_candidates` відбирає кандидатів |
| Пошук по дереву | beam-search / alpha-beta (не MCTS) |
| Chance/приховане | **детермінізація** (те, чого в AlphaZero немає) |

Тобто `PolicyCriticBot` — це вже «AlphaZero-подібна» декомпозиція (policy пропонує,
value оцінює), але начеплена на **beam-search з детермінізацією** замість MCTS над
інформаційними сетами. Саме стик «AlphaZero ↔ неповна інформація» і є місцем, де
детермінізація стає вузьким місцем.

## 6. Кращі рішення (за зростанням складності)

### 6.1 Дешеві покращення поточного підходу

**(a) Правильний PIMC замість зваженого голосування.** Поточна схема голосує
`0.8/0.2` вагами за *дію-переможця* кожного підпошуку. Канонічний PIMC натомість
усереднює **цінність кожної кореневої дії** по світах і бере argmax середнього:

```
для кожної кореневої дії a:  Q(a) = (1/K) Σ_world  value(a | world)
обрати argmax_a Q(a)
```

Це зменшує дисперсію коректніше, ніж голосування (голосування втрачає інформацію
про *наскільки* дія краща). Але спершу треба зняти проблему глибини (нижче), бо
зараз розбиття бюджету програє через голод на глибину.

**(b) Точне матсподівання на найдрібнішому chance-вузлі.** Замість одного
вгаданого порядку — на **першому** доборі (найвпливовішому) порахувати
матсподівання точно: наступна монета рівномірна над невеликою мультимножиною
мішка, тож можна розгалузитись на всі унікальні монети з їх імовірностями
(expectiminimax лише на кореневому chance-вузлі), а глибші добори лишити
детермінізованими. Дешево і прибирає найбільшу частину дисперсії §3.

**(c) Belief-зважена детермінізація (particle filter).** У fair-режимі замість
рівномірного перерозбиття семплувати руку опонента з розподілу, **умовного** на
тому, що він показав (face-up скиди, зіграні монети, історія recruit). Мінімум —
не рівномірно, а пропорційно до правдоподібності. Це прямо лікує §4.3 і робить
чесний режим придатним для реальної гри.

**(d) Транспозиційна таблиця / кешування.** Уже є `_survivor_cache` по шляху; його
можна розширити до кешу за *станом* (transposition table), щоб різні порядки ходів,
які ведуть в ту саму позицію, ділили оцінку — це вивільняє бюджет під (a).

### 6.2 Information Set MCTS (IS-MCTS) — принципова заміна

Замість «детермінізуй → розв'яжи повну гру» тримати **одне дерево над
інформаційними сетами**. На кожній ітерації семплується детермінізація, спуск по
дереву йде лише через вузли, **сумісні** з нею, але статистика (візити, цінності)
накопичується **на рівні інформаційного сету**, а не конкретного світу. Тому
рішення в одному info-set вимушено єдине для всіх сумісних світів — це прямо усуває
**strategy fusion** (§4.1).

Варіанти: **SO-ISMCTS** (single-observer) та **MO-ISMCTS** (multiple-observer,
моделює й приховану інформацію опонента окремим деревом). Для Сундука Війни, де
приховане — лише порядок/розбиття *відомих* монет, IS-MCTS лягає особливо добре:
семплувати детермінізацію дешево, а `Critic`/`Policy` вже готові дати value/prior
у вузлах — це і буде справжній «AlphaZero для неповної інформації»:

```
IS-MCTS + Policy(prior) + Critic(value) ≈ AlphaZero, адаптований під info-sets
```

Це найкраще співвідношення «принциповість / зусилля» саме для цієї гри і напряму
відповідає тому, чого намагається досягти користувач.

### 6.3 CFR / ReBeL — теоретично найправильніше

Для ігор з неповною інформацією теоретично коректний підхід — **counterfactual
regret minimization** над belief-станами. **DeepStack** та **ReBeL** поєднують
CFR-пошук у підгрі з навченою value-мережею над *розподілами belief* — це і є
буквальний «AlphaZero для покеру». Дає стратегії, стійкі до експлуатації (Nash),
чого детермінізація принципово не гарантує.

Ціна: треба міряти цінність не окремого стану, а **belief-стану** (розподілу над
руками), і гру трактувати як послідовність публічних станів з приватними
розподілами. Для Сундука Війни це реально (приховане — мала, дискретна множина), але
це значний обсяг роботи й найважчий шлях. Розумно як довгострокова ціль, якщо
з'явиться потреба в неексплуатовності (пор. [next_steps.md](next_steps.md) про
exploitability/Nash).

## 7. Рекомендація

Порядок дій за співвідношенням користь/зусилля:

1. **Зараз:** додати belief-зважену детермінізацію (§6.1c) — це єдине, що робить
   *чесний* режим життєздатним, і потрібне для реальної гри в вебі.
2. **Далі:** зняти голод на глибину (транспозиції §6.1d) і перейти на коректне
   PIMC-усереднення цінності дій (§6.1a) + точне матсподівання на першому доборі
   (§6.1b). Це вичавлює максимум із поточної архітектури дешево.
3. **Стратегічно:** переписати ядро пошуку на **IS-MCTS з `Policy`+`Critic`**
   (§6.2). Це і є AlphaZero-подібний пошук, коректно узгоджений з неповною
